# 技術決策紀錄

每一條的格式：**決策**／考慮過的選項／選擇的理由／取捨。依時間順序排列。

---

## 規劃階段

### 1. LLM 使用 Google Gemini API 免費方案
- **考慮過的選項**：Gemini 免費方案、Groq 免費方案（Llama 等開源模型）、OpenAI／Claude（付費）、本機 Ollama
- **選擇的理由**：免費、不需要信用卡；Flash 系列的品質足夠產生單字解釋和例句；支援 JSON 結構化輸出，適合批次處理
- **取捨**：
  - 免費額度有每分鐘和每天的請求上限，而且數字常常改，所以程式要能限速、重試，模型也不能寫死（見第 16 條）
  - 免費方案下 Google 可能用送出的內容改進模型，但送出的只有英文單字，可以接受
  - 不用 Ollama：網站公開後，其他人連不到使用者電腦上的模型
  - Groq 保留為備案

### 2. 讓使用者自己填 API 金鑰，網站維持純前端
- **考慮過的選項**：使用者自己填金鑰（存在瀏覽器）、加一層小後端（Vercel／Cloudflare Workers）把金鑰放在環境變數
- **選擇的理由**：不需要架設和維護伺服器，可以直接部署到 GitHub Pages；金鑰永遠不會出現在程式碼或 GitHub 上
- **取捨**：使用者要自己去 Google AI Studio 申請金鑰，多一個步驟。所以沒有金鑰時，字典和簡易測驗也要能正常使用。之後如果想讓使用者免申請，可以再加後端

### 3. 字典＋LLM 混合取得單字資料
- **考慮過的選項**：全部交給 LLM、全部用字典、兩者混合
- **選擇的理由**：
  - 字典（ECDICT）免費、可靠、離線也能查，可以立刻顯示中文
  - LLM 補上字典做不到的部分：「多益最常考的意思」、淺白英文解釋、例句、搭配詞
- **取捨**：要處理兩種資料來源的合併規則（見第 17 條）。字典的意思比較廣、不一定是多益考的意思，例如 *warranty* 第一個意思是「正當理由」

### 4. 部署在 GitHub Pages
- **考慮過的選項**：GitHub Pages、Cloudflare Pages、Vercel、Netlify
- **選擇的理由**：純前端網站直接 push 就能自動更新、全程免費，而且程式碼和網站在同一個地方，適合作品集
- **取捨**：只能放靜態檔案，不能有後端函式。如果之後要做第 2 條的後端，再搬到 Cloudflare 或 Vercel

### 5. 資料存在瀏覽器（localStorage）
- **考慮過的選項**：localStorage、IndexedDB、雲端資料庫（Firebase／Supabase）
- **選擇的理由**：不需要帳號系統；幾千個單字的 JSON 只有幾百 KB，在 localStorage 約 5MB 的上限內；API 是同步的，程式比較簡單
- **取捨**：不同裝置之間不會同步，清除瀏覽器資料就會消失，所以第 8 步要做匯出／匯入。如果資料量變大，可以改用 IndexedDB

## 第 1 步：專案骨架

### 6. 純 HTML／CSS／JavaScript（ES modules），不使用框架和建置工具
- **考慮過的選項**：React＋Vite、Vue、純 JavaScript
- **選擇的理由**：不需要 `npm install` 和建置步驟，放上 GitHub Pages 就能直接跑；使用者是初學者，打開檔案就看得懂；這個網站的畫面狀態不複雜
- **取捨**：要自己寫簡單的路由（`#/cards`）和「資料變更 → 重畫畫面」的通知機制（`store.subscribe`）。如果功能變得很複雜，這部分會比較費工

## 第 2 步：字典與發音

### 7. 只放 ECDICT 的常用字子集，並依首字母拆成 26 個檔案
- **考慮過的選項**：整本字典（77 萬字、66MB）、呼叫線上字典 API、取常用字子集
- **選擇的理由**：
  - 只留詞頻前 3 萬、考試標籤、柯林斯星級或牛津 3000 的字，共 32,812 字、2.75MB
  - 依首字母拆檔，查 *approve* 只會下載 `a.json`（最大的檔案也只有 342KB）
- **取捨**：罕見字查不到，這時交給 LLM 或讓使用者手動填。原始的大檔不上傳 GitHub，改附上轉換腳本 `tools/build_dict.py`，需要時可以重新產生

### 8. 用 OpenCC 的 `s2twp` 設定把簡體轉成繁體
- **考慮過的選項**：`s2t`（只轉字）、`s2tw`（台灣字形）、`s2twp`（台灣字形＋台灣用語）
- **選擇的理由**：`s2twp` 連用詞都會轉，例如「软件」→「軟體」，更符合台灣使用者的習慣
- **取捨**：用詞轉換偶爾會過度轉換。轉換只在產生字典時做一次，所以網站不需要載入 OpenCC

### 9. 片語不放進本機字典，交給 LLM
- **考慮過的選項**：把 ECDICT 的片語一起放進去、不放
- **選擇的理由**：ECDICT 有 25 萬條片語，放進來檔案會大好幾倍；而且片語在多益的用法更需要上下文，由 LLM 生成效果比較好
- **取捨**：沒有金鑰時，片語（例如 *take over*）只能手動填寫

### 10. Free Dictionary API 失敗時分成「查無此字」和「暫時出錯」
- **背景**：開發時 Free Dictionary API 剛好掛掉（HTTP 522）
- **考慮過的選項**：失敗就放棄、每次開網站都重查、依失敗原因分開處理
- **選擇的理由**：404（查無此字）不再重查，以免浪費請求；網路錯誤或 5xx 會在下次開網站時自動重試
- **取捨**：每個字要多記一個 `lookup.enDone` 狀態

### 11. 發音使用瀏覽器內建的 Web Speech API
- **考慮過的選項**：Web Speech API、字典 API 附的音檔、文字轉語音雲端服務
- **選擇的理由**：免費、不需要金鑰、離線也能用，可以切換美式／英式口音和速度
- **取捨**：音質依作業系統和瀏覽器而不同，程式會優先挑名稱含 Natural、Google 的較好語音

## 第 3 步：批次新增

### 12. 查詢分成兩個階段：本機字典整批處理，線上 API 排隊處理
- **考慮過的選項**：每個字依序完整查完、兩階段
- **選擇的理由**：中文意思來自本機，100 個字 0.26 秒就能全部顯示；英文解釋要連網，所以排隊並間隔 250ms，避免被 API 擋掉
- **取捨**：程式多了一個階段。另外新增 `updateWords()`，一次更新多個字但只寫入 localStorage 一次

### 13. 拆字規則：用「小字」判斷是不是片語
- **問題**：使用者說「空白也可以分隔」，但 *take over* 這種片語本身就有空白
- **考慮過的選項**：空白一律拆開、要求片語加引號、用規則判斷
- **選擇的理由**：如果有空白的那一段是 2～4 個字，而且後面含有 up、over、of、to、for 等小字，就當成片語，否則依空白拆開。中文、編號、項目符號一律當成分隔符號，這樣直接從講義或網頁貼上也能用
- **取捨**：少數名詞片語（例如 *annual report*）會被拆成兩個字，但加入前的預覽會清楚顯示結果。拆字邏輯寫成純函式 `splitWords()`／`analyzeInput()`，可以單獨測試

## 第 4 步：Gemini 批次生成

### 14. 每個請求放 20 個字，用 JSON Schema 規定輸出格式
- **考慮過的選項**：一個字一個請求、一批 20 個字
- **選擇的理由**：免費額度的瓶頸是「請求次數」而不是 token 數，20 個字一批可以省下 95% 的請求；`responseSchema` 讓 Gemini 一定回傳可以解析的 JSON
- **取捨**：一批越大，回應越可能被截斷（`MAX_TOKENS`）。被截斷時會自動把這批拆成兩半重送。如果漏掉某個字，只把那個字標成失敗，可以單獨重試

### 15. 限速採用「依每分鐘請求上限平均間隔」，429 時依 Google 建議的時間等待
- **考慮過的選項**：失敗了才重試、固定間隔、讓使用者設定每分鐘請求上限
- **選擇的理由**：
  - 依使用者設定的每分鐘請求上限平均分配間隔，預設是保守的 5 次／分
  - 429 時讀取 Google 回應中的 `RetryInfo.retryDelay` 再重試，沒有的話就依 15、30、60 秒退避，最多重試 3 次
  - 畫面上會顯示倒數，使用者知道程式還在跑
- **取捨**：
  - 預設值很保守，速度比實際額度允許的慢
  - 額度用完時整個佇列會停下來，但這些字不算失敗，之後可以直接再按「生成」

### 16. 不把模型名稱寫死，用金鑰向 Google 查詢可用的模型
- **考慮過的選項**：寫死某個模型名稱、使用者手動輸入、動態查詢
- **選擇的理由**：Gemini 的模型名稱和免費方案常常變動，寫死的名稱可能哪天就失效。「儲存並檢查」會呼叫 ListModels，同時驗證金鑰，並自動挑出最新的 Flash 模型（排除 Pro、圖片和嵌入模型）
- **取捨**：清單只在這次開啟網站時記住；如果查詢失敗，會使用 `gemini-flash-latest` 這個別名

### 17. 每個欄位都記錄資料來源，保護使用者手動修改的內容
- **考慮過的選項**：AI 一律覆蓋、AI 只填空白欄位、依來源決定
- **選擇的理由**：
  - 每個欄位記錄來源 `src`，可能是 `dict`、`freedict`、`llm` 或 `user`
  - AI 可以覆蓋字典的內容，因為 AI 的內容更貼近多益
  - 使用者手動改過的欄位一律保留
- **取捨**：資料結構多了一層。編輯視窗要比對哪些欄位真的有被改過，包括例句、搭配詞這類清單欄位

### 18. API 金鑰放在 HTTP 標頭，不放在網址
- **考慮過的選項**：網址參數 `?key=`、標頭 `x-goog-api-key`
- **選擇的理由**：網址容易出現在瀏覽器紀錄、伺服器日誌或截圖裡，放在標頭比較安全。金鑰存在獨立的 localStorage 欄位，之後的匯出功能不會把它一起匯出
- **取捨**：沒有

### 19. 有金鑰時跳過 Free Dictionary
- **選擇的理由**：AI 的英文解釋會取代 Free Dictionary 的解釋，所以有金鑰時就不再查 Free Dictionary，省下請求和時間。只有 AI 生成失敗的字，才回頭用 Free Dictionary 補
- **取捨**：沒有

### 20. 測試全部使用假的外部服務（mock）
- **考慮過的選項**：測試時呼叫真的 API、用 Playwright 攔截請求並回傳假資料
- **選擇的理由**：
  - 真的 API 會掛（Free Dictionary 就掛過）、會用掉額度，也需要金鑰
  - 假回應可以穩定重現 429、截斷、錯誤金鑰等很難遇到的情況
- **取捨**：沒辦法驗證真的 Gemini 回傳的內容品質，這部分要用真金鑰手動確認

## 第 5 步：間隔重複與滑卡手勢

### 21. 間隔重複用簡化版 SM-2，只有「會／不熟」兩個按鈕
- **考慮過的選項**：Anki 的四個按鈕（重來／困難／良好／簡單）、FSRS（新一代演算法）、簡化 SM-2 搭配兩個按鈕
- **選擇的理由**：
  - 兩個選項剛好對應左右滑，手機上一隻手就能操作
  - SM-2 的規則簡單，容易理解和測試：答「會」時，間隔依 1 天、3 天，之後乘上 ease 增加；答「不熟」就 10 分鐘後再出現
  - 寫成純函式（`js/srs.js`），用 Node 就能做單元測試
- **取捨**：沒有「困難」「簡單」可以微調間隔，只能靠 ease 慢慢調整。FSRS 比較準，但需要累積資料來訓練參數，對個人背單字來說太複雜

### 22. 一天從早上 4 點開始算
- **考慮過的選項**：午夜 0 點、早上 4 點
- **選擇的理由**：學生常常半夜才複習。用 0 點換日的話，晚上 11 點複習的字到了凌晨 1 點就「隔天到期」了，排程會亂掉。Anki 也是用早上 4 點換日
- **取捨**：凌晨 0 點到 4 點的紀錄會算在前一天

### 23. 「不熟」標記和複習結果連動
- **考慮過的選項**：只能手動標記、答錯自動標記但不會自動取消、答錯自動標記且熟了自動取消
- **選擇的理由**：答「不熟」就自動標記，「不熟」清單才會反映真實狀況；間隔達到 21 天代表已經很熟了，就自動取消，不然清單只會越來越長
- **取捨**：使用者手動標記的「不熟」，也可能在達到 21 天時被取消

### 24. 滑卡模組自己判斷「點一下」，不依賴瀏覽器的 click
- **背景**：Chrome 在快速滑動後大約 1 秒內，會把下一次點擊當成「停止慣性」而不送出 `click`，導致滑完一張後馬上點下一張卻翻不了面
- **考慮過的選項**：只用 click、自己用 pointerdown／pointerup 判斷點擊
- **選擇的理由**：移動不到 8px、時間少於 600ms 就算「點一下」，直接呼叫 `onTap`，並擋掉之後跟著來的 click 避免重複；用鍵盤觸發的 click 照常處理
- **取捨**：要多處理「擋掉重複的 click」這件事

### 25. 複習頁成為首頁，原本的字卡頁改為「自由瀏覽」
- **選擇的理由**：每天打開網站，最重要的事是完成今天的複習。瀏覽頁保留給想隨意翻看或只看不熟字的時候使用，而且在瀏覽頁滑動不會影響複習排程
- **取捨**：導覽列多了一個項目，手機上要把文字和間距縮小

## 第 6 步：測驗與錯題本

### 26. 簡易測驗的錯誤選項：同詞性優先，用「選項文字」判斷是否重複
- **考慮過的選項**：完全隨機挑、同詞性優先、用 AI 挑
- **選擇的理由**：
  - 同詞性的選項比較像真的考題，不能只靠詞性就猜出答案
  - 判斷重複要用選項上實際顯示的文字。例如在聽力題裡，*invoice* 和 *bill* 的中文都是「發票」，所以不能同時出現
  - 不需要 AI，沒有金鑰也能考
- **取捨**：字卡裡同詞性的字太少時，會改用其他詞性補，題目就比較簡單

### 27. Part 5 的錯誤選項由程式從字卡挑，再請 AI 改成相同詞形，並且驗證 AI 出的題目
- **考慮過的選項**：讓 AI 自己想錯誤選項、從字卡挑
- **選擇的理由**：
  - 規格要求「錯誤選項優先從使用者字卡中的其他單字挑」，這樣考的是自己正在背的字，複習效果更好
  - 程式先挑好錯誤選項（同詞性優先），再請 AI 改成和答案一樣的詞形（例如都改成過去式），這樣四個選項看起來才像真的考題
  - AI 偶爾會出錯，所以每題都要用 `normalizePart5()` 檢查：只能有一個空格、四個選項不重複、答案不能已經出現在句子裡；不合格的題目就丟掉
- **取捨**：被丟掉的題目，那個字這次就不考。畫面會提示「有 N 個字出題失敗」，下次會再試

### 28. Part 5 題目存在單字上重複使用
- **考慮過的選項**：每次都重新出題、存起來重複使用
- **選擇的理由**：
  - 免費額度有限，每個字最多存 3 題，出題時優先用最久沒考過的那題
  - 選項的順序每次都會重新打亂，避免記住答案的位置
  - 想要新題目時，可以勾選「出新題目」
- **取捨**：存檔的題目考久了可能會記住句子，所以提供「出新題目」選項。題目存在單字資料裡，之後匯出／匯入時會一起帶走

### 29. 錯題本存「整題」，而不是只存單字
- **考慮過的選項**：只記哪些字答錯、存完整的題目
- **選擇的理由**：重做時看到的是同一題（特別是 Part 5 的句子），不需要再呼叫 AI。同一題重複答錯時，只把次數加 1，不會重複存
- **取捨**：比較佔空間，所以最多存 300 題。刪除單字時，相關的錯題也會一起清掉

### 30. 測驗答錯只標記「不熟」，不改變複習排程
- **考慮過的選項**：答錯時也把複習排程重設成「10 分鐘後到期」、只標記不熟
- **選擇的理由**：規格是「答錯的字自動標記為不熟」。複習排程只由「複習」頁決定，兩者分開比較好理解，也不會因為測驗時手滑點錯就打亂排程
- **取捨**：測驗答錯的字不會馬上出現在複習清單裡，但可以用「不熟」的範圍去瀏覽或測驗

### 31. 「檢查」和「寫入」之間不能有等待（避免非同步的競態）
- **背景**：一次加入很多字時，字典資料偶爾會蓋掉 AI 剛生成的中文。原因是舊程式先算好要寫入的字典資料，等其他字母的檔案下載完才寫入，這段期間 AI 可能已經寫好了內容
- **考慮過的選項**：每個字查完馬上寫入、加上鎖、先下載完再一次檢查並寫入
- **選擇的理由**：先 `await` 下載好所有需要的字典檔，再同步地讀取最新資料、檢查是否可以寫入、寫入。JavaScript 是單執行緒，同步執行的這一段不會被 AI 的回應插進來
- **取捨**：中文要等這一批的字典檔都下載完才會一起出現，但字典檔在本機，通常不到 1 秒就好

## 第 7 步：學習統計

### 32. 圖表自己用 SVG 畫，不使用圖表套件
- **考慮過的選項**：Chart.js、ECharts、自己用 SVG 畫
- **選擇的理由**：
  - 只需要直條圖一種，自己寫大約 200 行
  - 不需要從外部 CDN 載入套件，第 9 步做 PWA 時離線也能看統計
  - 可以完全照 dataviz 規範控制細節：柱子寬度、圓角、2px 空隙、只標最高值、提示框、表格
- **取捨**：功能比套件少（沒有動畫、縮放），之後如果需要更複雜的圖表，再考慮使用套件

### 33. 「會／不熟」用藍／橘兩個系列色，不用綠／紅
- **考慮過的選項**：綠／紅、藍／橘
- **選擇的理由**：依照 dataviz 規範，綠、紅這類狀態色是保留給「狀態」用的（例如成功、錯誤），而且必須搭配圖示和文字。這裡的兩個系列是分類，所以用系列色。藍／橘兩色用 `validate_palette.js` 對本站的卡片底色驗證：淺色、深色模式都通過，色盲模擬下的色差是 24.7 和 26.8（門檻 8）
- **取捨**：「答錯是橘色」不像紅色那麼直覺，但有圖例和文字標示，不會只靠顏色判斷

### 34. 熟練度用同一個藍色的深淺；深色模式另外挑色並驗證
- **選擇的理由**：
  - 新字 → 學習中 → 熟悉中 → 已熟是「有順序的分組」，所以用同一個色相由淺到深，不用四種不同顏色
  - 深色模式改成「越熟越亮」，因為在深色背景上，越亮越顯眼
  - 第一次挑的深色色階中，最深一階對本站的深灰底色只有 1.87:1，驗證沒有通過；往淺一階換成 `#1c5cab`（2.28:1）才通過
- **取捨**：深色模式要多維護一組顏色，但這些顏色都集中定義在 CSS 變數裡

### 35. 連續學習天數：今天還沒學習時，從昨天開始算
- **考慮過的選項**：嚴格只算到今天（今天沒學就是 0）、今天還沒學時從昨天開始算
- **選擇的理由**：一大早打開網站就看到「連續 0 天」會很打擊信心。從昨天開始算，並提示「今天學習一下就能延續！」，比較能鼓勵使用者。只做測驗、沒有複習，也算有學習
- **取捨**：這個數字代表「到昨天為止」還是「到今天為止」，要看旁邊的提示文字

### 36. 「設定」改成齒輪圖示
- **選擇的理由**：加上「統計」後有 6 個文字項目，手機上排不下，文字還被折成兩行。設定不是每天都會用到，改成和深色模式按鈕並排的圖示（有 `aria-label`）
- **取捨**：設定的入口比較不明顯，但齒輪是大家都認得的圖示

## 第 8 步：匯出／匯入（含追加的口音與每日目標）

### 37. 「多益混合」口音：只從這台裝置有語音的口音中隨機挑
- **背景**：使用者要求加入多益聽力的四種口音（美、英、加、澳）
- **考慮過的選項**：固定一種口音、四種輪流（不管裝置有沒有）、只挑有語音的口音
- **選擇的理由**：
  - 發音靠的是裝置內建的語音（Web Speech API）。如果裝置沒有加拿大語音卻硬要選，瀏覽器會用預設的美式語音，等於「標示是加拿大，聽起來是美國」，這樣會誤導
  - 所以混合模式只挑有語音的口音；手動選了沒有語音的口音時，設定頁會直接說明會用其他語音代替
- **取捨**：可以練到的口音受裝置限制。設定頁有教使用者怎麼新增語音
- **沒有用 AI 產生語音**：Gemini 有語音模型，但需要網路、會用掉額度，而且每個字都要另外處理；內建語音免費又能離線使用，已經夠用

### 38. 只擋滑鼠或觸控產生的重複 click，鍵盤的 click 一律放行
- **背景**：決策 #24 為了避免「點一下」觸發兩次，會擋掉點擊後短時間內的 click，結果連鍵盤觸發的按鈕也被擋掉了
- **選擇的理由**：瀏覽器會把鍵盤觸發的 click 標成 `event.detail === 0`，滑鼠或觸控的則是 1 以上，用這個就能精準區分
- **取捨**：沒有

### 39. 每日目標：達標才算打卡；每天記下當天的目標
- **考慮過的選項**：有學習就算打卡、達標才算打卡、兩種都顯示
- **選擇的理由**：
  - 使用者選了「達標才算」，比較有督促的效果
  - 目標記在每天的紀錄裡，之後調整目標不會改寫過去的打卡；但今天一律用目前的目標，今天把目標調高就要重新達標
  - 複習一張卡或測驗答一題都算 1 題，兩種學習方式都能累積進度
- **取捨**：紀錄多一個欄位；舊資料沒有記下目標，就用目前的目標判斷

### 40. 備份檔不包含 Gemini 金鑰
- **選擇的理由**：備份檔常常會被傳來傳去（寄給自己、放雲端、傳給朋友），金鑰放在裡面很容易外洩。金鑰本來就存在獨立的 localStorage 欄位，匯出時根本不會讀到它
- **取捨**：換裝置後要重新填一次金鑰。設定頁有說明

### 41. 匯入時每個欄位都重新檢查和清理
- **考慮過的選項**：直接寫入、只檢查格式、逐欄清理
- **選擇的理由**：備份檔可能被改過、壞掉，或根本是別的檔案。逐欄清理的做法：
  - 型別不對就改成預設值，數字限制在合理範圍
  - 不認得的設定和欄位丟掉
  - 錯題的選項必須剛好 4 個
  - 單字必須含有英文字母
- **取捨**：程式比較長，但壞檔案不會讓網站壞掉。另外畫面一律跳脫 HTML，被竄改的內容也不會被執行（有測試驗證）

### 42. 合併的規則：最後修改的版本勝出，每日紀錄取較大值
- **考慮過的選項**：一律以備份為主、一律以目前為主、依修改時間決定
- **選擇的理由**：
  - 同一個字，留下 `updatedAt` 比較新的版本，哪台裝置最後改過就以哪台為準
  - 每日紀錄同一天的每個欄位取較大值，而不是相加。這樣同一份備份匯入兩次結果也不會變，使用者不小心重複匯入也沒關係
- **取捨**：如果兩台裝置在同一天都有複習，合併後的次數會偏少（取較大值，而不是相加）。這是為了避免重複計算所做的選擇；真正的跨裝置同步要等之後接上雲端資料庫
