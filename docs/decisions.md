# 技術決策紀錄

每一條的格式：**決策**／考慮過的選項／選擇的理由／取捨。依時間順序排列。

---

## 規劃階段

### 1. LLM 使用 Google Gemini API 免費方案
- **考慮過的選項**：Gemini 免費方案、Groq 免費方案（Llama 等開源模型）、OpenAI／Claude（付費）、本機 Ollama
- **選擇的理由**：免費、不需要信用卡；Flash 系列的品質足夠產生單字解釋和例句；支援 JSON 結構化輸出，適合批次處理
- **取捨**：
  - 免費額度有每分鐘和每天的請求上限，而且數字常常改，所以程式要能限速、重試，模型也不能寫死（見第 16 條）
  - 免費方案下 Google 可能用送出的內容改進模型，但送出的只有英文單字，可以接受
  - 不用 Ollama：網站公開後，其他人連不到使用者電腦上的模型
  - Groq 保留為備案

### 2. 讓使用者自己填 API 金鑰，網站維持純前端
- **考慮過的選項**：使用者自己填金鑰（存在瀏覽器）、加一層小後端（Vercel／Cloudflare Workers）把金鑰放在環境變數
- **選擇的理由**：不需要架設和維護伺服器，可以直接部署到 GitHub Pages；金鑰永遠不會出現在程式碼或 GitHub 上
- **取捨**：使用者要自己去 Google AI Studio 申請金鑰，多一個步驟。所以沒有金鑰時，字典和簡易測驗也要能正常使用。之後如果想讓使用者免申請，可以再加後端

### 3. 字典＋LLM 混合取得單字資料
- **考慮過的選項**：全部交給 LLM、全部用字典、兩者混合
- **選擇的理由**：
  - 字典（ECDICT）免費、可靠、離線也能查，可以立刻顯示中文
  - LLM 補上字典做不到的部分：「多益最常考的意思」、淺白英文解釋、例句、搭配詞
- **取捨**：要處理兩種資料來源的合併規則（見第 17 條）。字典的意思比較廣、不一定是多益考的意思，例如 *warranty* 第一個意思是「正當理由」

### 4. 部署在 GitHub Pages
- **考慮過的選項**：GitHub Pages、Cloudflare Pages、Vercel、Netlify
- **選擇的理由**：純前端網站直接 push 就能自動更新、全程免費，而且程式碼和網站在同一個地方，適合作品集
- **取捨**：只能放靜態檔案，不能有後端函式。如果之後要做第 2 條的後端，再搬到 Cloudflare 或 Vercel

### 5. 資料存在瀏覽器（localStorage）
- **考慮過的選項**：localStorage、IndexedDB、雲端資料庫（Firebase／Supabase）
- **選擇的理由**：不需要帳號系統；幾千個單字的 JSON 只有幾百 KB，在 localStorage 約 5MB 的上限內；API 是同步的，程式比較簡單
- **取捨**：不同裝置之間不會同步，清除瀏覽器資料就會消失，所以第 8 步要做匯出／匯入。如果資料量變大，可以改用 IndexedDB

## 第 1 步：專案骨架

### 6. 純 HTML／CSS／JavaScript（ES modules），不使用框架和建置工具
- **考慮過的選項**：React＋Vite、Vue、純 JavaScript
- **選擇的理由**：不需要 `npm install` 和建置步驟，放上 GitHub Pages 就能直接跑；使用者是初學者，打開檔案就看得懂；這個網站的畫面狀態不複雜
- **取捨**：要自己寫簡單的路由（`#/cards`）和「資料變更 → 重畫畫面」的通知機制（`store.subscribe`）。如果功能變得很複雜，這部分會比較費工

## 第 2 步：字典與發音

### 7. 只放 ECDICT 的常用字子集，並依首字母拆成 26 個檔案
- **考慮過的選項**：整本字典（77 萬字、66MB）、呼叫線上字典 API、取常用字子集
- **選擇的理由**：
  - 只留詞頻前 3 萬、考試標籤、柯林斯星級或牛津 3000 的字，共 32,812 字、2.75MB
  - 依首字母拆檔，查 *approve* 只會下載 `a.json`（最大的檔案也只有 342KB）
- **取捨**：罕見字查不到，這時交給 LLM 或讓使用者手動填。原始的大檔不上傳 GitHub，改附上轉換腳本 `tools/build_dict.py`，需要時可以重新產生

### 8. 用 OpenCC 的 `s2twp` 設定把簡體轉成繁體
- **考慮過的選項**：`s2t`（只轉字）、`s2tw`（台灣字形）、`s2twp`（台灣字形＋台灣用語）
- **選擇的理由**：`s2twp` 連用詞都會轉，例如「软件」→「軟體」，更符合台灣使用者的習慣
- **取捨**：用詞轉換偶爾會過度轉換。轉換只在產生字典時做一次，所以網站不需要載入 OpenCC

### 9. 片語不放進本機字典，交給 LLM
- **考慮過的選項**：把 ECDICT 的片語一起放進去、不放
- **選擇的理由**：ECDICT 有 25 萬條片語，放進來檔案會大好幾倍；而且片語在多益的用法更需要上下文，由 LLM 生成效果比較好
- **取捨**：沒有金鑰時，片語（例如 *take over*）只能手動填寫

### 10. Free Dictionary API 失敗時分成「查無此字」和「暫時出錯」
- **背景**：開發時 Free Dictionary API 剛好掛掉（HTTP 522）
- **考慮過的選項**：失敗就放棄、每次開網站都重查、依失敗原因分開處理
- **選擇的理由**：404（查無此字）不再重查，以免浪費請求；網路錯誤或 5xx 會在下次開網站時自動重試
- **取捨**：每個字要多記一個 `lookup.enDone` 狀態

### 11. 發音使用瀏覽器內建的 Web Speech API
- **考慮過的選項**：Web Speech API、字典 API 附的音檔、文字轉語音雲端服務
- **選擇的理由**：免費、不需要金鑰、離線也能用，可以切換美式／英式口音和速度
- **取捨**：音質依作業系統和瀏覽器而不同，程式會優先挑名稱含 Natural、Google 的較好語音

## 第 3 步：批次新增

### 12. 查詢分成兩個階段：本機字典整批處理，線上 API 排隊處理
- **考慮過的選項**：每個字依序完整查完、兩階段
- **選擇的理由**：中文意思來自本機，100 個字 0.26 秒就能全部顯示；英文解釋要連網，所以排隊並間隔 250ms，避免被 API 擋掉
- **取捨**：程式多了一個階段。另外新增 `updateWords()`，一次更新多個字但只寫入 localStorage 一次

### 13. 拆字規則：用「小字」判斷是不是片語
- **問題**：使用者說「空白也可以分隔」，但 *take over* 這種片語本身就有空白
- **考慮過的選項**：空白一律拆開、要求片語加引號、用規則判斷
- **選擇的理由**：如果有空白的那一段是 2～4 個字，而且後面含有 up、over、of、to、for 等小字，就當成片語，否則依空白拆開。中文、編號、項目符號一律當成分隔符號，這樣直接從講義或網頁貼上也能用
- **取捨**：少數名詞片語（例如 *annual report*）會被拆成兩個字，但加入前的預覽會清楚顯示結果。拆字邏輯寫成純函式 `splitWords()`／`analyzeInput()`，可以單獨測試

## 第 4 步：Gemini 批次生成

### 14. 每個請求放 20 個字，用 JSON Schema 規定輸出格式
- **考慮過的選項**：一個字一個請求、一批 20 個字
- **選擇的理由**：免費額度的瓶頸是「請求次數」而不是 token 數，20 個字一批可以省下 95% 的請求；`responseSchema` 讓 Gemini 一定回傳可以解析的 JSON
- **取捨**：一批越大，回應越可能被截斷（`MAX_TOKENS`）。被截斷時會自動把這批拆成兩半重送。如果漏掉某個字，只把那個字標成失敗，可以單獨重試

### 15. 限速採用「依每分鐘請求上限平均間隔」，429 時依 Google 建議的時間等待
- **考慮過的選項**：失敗了才重試、固定間隔、讓使用者設定每分鐘請求上限
- **選擇的理由**：
  - 依使用者設定的每分鐘請求上限平均分配間隔，預設是保守的 5 次／分
  - 429 時讀取 Google 回應中的 `RetryInfo.retryDelay` 再重試，沒有的話就依 15、30、60 秒退避，最多重試 3 次
  - 畫面上會顯示倒數，使用者知道程式還在跑
- **取捨**：
  - 預設值很保守，速度比實際額度允許的慢
  - 額度用完時整個佇列會停下來，但這些字不算失敗，之後可以直接再按「生成」

### 16. 不把模型名稱寫死，用金鑰向 Google 查詢可用的模型
- **考慮過的選項**：寫死某個模型名稱、使用者手動輸入、動態查詢
- **選擇的理由**：Gemini 的模型名稱和免費方案常常變動，寫死的名稱可能哪天就失效。「儲存並檢查」會呼叫 ListModels，同時驗證金鑰，並自動挑出最新的 Flash 模型（排除 Pro、圖片和嵌入模型）
- **取捨**：清單只在這次開啟網站時記住；如果查詢失敗，會使用 `gemini-flash-latest` 這個別名

### 17. 每個欄位都記錄資料來源，保護使用者手動修改的內容
- **考慮過的選項**：AI 一律覆蓋、AI 只填空白欄位、依來源決定
- **選擇的理由**：
  - 每個欄位記錄來源 `src`，可能是 `dict`、`freedict`、`llm` 或 `user`
  - AI 可以覆蓋字典的內容，因為 AI 的內容更貼近多益
  - 使用者手動改過的欄位一律保留
- **取捨**：資料結構多了一層。編輯視窗要比對哪些欄位真的有被改過，包括例句、搭配詞這類清單欄位

### 18. API 金鑰放在 HTTP 標頭，不放在網址
- **考慮過的選項**：網址參數 `?key=`、標頭 `x-goog-api-key`
- **選擇的理由**：網址容易出現在瀏覽器紀錄、伺服器日誌或截圖裡，放在標頭比較安全。金鑰存在獨立的 localStorage 欄位，之後的匯出功能不會把它一起匯出
- **取捨**：沒有

### 19. 有金鑰時跳過 Free Dictionary
- **選擇的理由**：AI 的英文解釋會取代 Free Dictionary 的解釋，所以有金鑰時就不再查 Free Dictionary，省下請求和時間。只有 AI 生成失敗的字，才回頭用 Free Dictionary 補
- **取捨**：沒有

### 20. 測試全部使用假的外部服務（mock）
- **考慮過的選項**：測試時呼叫真的 API、用 Playwright 攔截請求並回傳假資料
- **選擇的理由**：
  - 真的 API 會掛（Free Dictionary 就掛過）、會用掉額度，也需要金鑰
  - 假回應可以穩定重現 429、截斷、錯誤金鑰等很難遇到的情況
- **取捨**：沒辦法驗證真的 Gemini 回傳的內容品質，這部分要用真金鑰手動確認

## 第 5 步：間隔重複與滑卡手勢

### 21. 間隔重複用簡化版 SM-2，只有「會／不熟」兩個按鈕
- **考慮過的選項**：Anki 的四個按鈕（重來／困難／良好／簡單）、FSRS（新一代演算法）、簡化 SM-2 搭配兩個按鈕
- **選擇的理由**：
  - 兩個選項剛好對應左右滑，手機上一隻手就能操作
  - SM-2 的規則簡單，容易理解和測試：答「會」時，間隔依 1 天、3 天，之後乘上 ease 增加；答「不熟」就 10 分鐘後再出現
  - 寫成純函式（`js/srs.js`），用 Node 就能做單元測試
- **取捨**：沒有「困難」「簡單」可以微調間隔，只能靠 ease 慢慢調整。FSRS 比較準，但需要累積資料來訓練參數，對個人背單字來說太複雜

### 22. 一天從早上 4 點開始算
- **考慮過的選項**：午夜 0 點、早上 4 點
- **選擇的理由**：學生常常半夜才複習。用 0 點換日的話，晚上 11 點複習的字到了凌晨 1 點就「隔天到期」了，排程會亂掉。Anki 也是用早上 4 點換日
- **取捨**：凌晨 0 點到 4 點的紀錄會算在前一天

### 23. 「不熟」標記和複習結果連動
- **考慮過的選項**：只能手動標記、答錯自動標記但不會自動取消、答錯自動標記且熟了自動取消
- **選擇的理由**：答「不熟」就自動標記，「不熟」清單才會反映真實狀況；間隔達到 21 天代表已經很熟了，就自動取消，不然清單只會越來越長
- **取捨**：使用者手動標記的「不熟」，也可能在達到 21 天時被取消

### 24. 滑卡模組自己判斷「點一下」，不依賴瀏覽器的 click
- **背景**：Chrome 在快速滑動後大約 1 秒內，會把下一次點擊當成「停止慣性」而不送出 `click`，導致滑完一張後馬上點下一張卻翻不了面
- **考慮過的選項**：只用 click、自己用 pointerdown／pointerup 判斷點擊
- **選擇的理由**：移動不到 8px、時間少於 600ms 就算「點一下」，直接呼叫 `onTap`，並擋掉之後跟著來的 click 避免重複；用鍵盤觸發的 click 照常處理
- **取捨**：要多處理「擋掉重複的 click」這件事

### 25. 複習頁成為首頁，原本的字卡頁改為「自由瀏覽」
- **選擇的理由**：每天打開網站，最重要的事是完成今天的複習。瀏覽頁保留給想隨意翻看或只看不熟字的時候使用，而且在瀏覽頁滑動不會影響複習排程
- **取捨**：導覽列多了一個項目，手機上要把文字和間距縮小

## 第 6 步：測驗與錯題本

### 26. 簡易測驗的錯誤選項：同詞性優先，用「選項文字」判斷是否重複
- **考慮過的選項**：完全隨機挑、同詞性優先、用 AI 挑
- **選擇的理由**：
  - 同詞性的選項比較像真的考題，不能只靠詞性就猜出答案
  - 判斷重複要用選項上實際顯示的文字。例如在聽力題裡，*invoice* 和 *bill* 的中文都是「發票」，所以不能同時出現
  - 不需要 AI，沒有金鑰也能考
- **取捨**：字卡裡同詞性的字太少時，會改用其他詞性補，題目就比較簡單

### 27. Part 5 的錯誤選項由程式從字卡挑，再請 AI 改成相同詞形，並且驗證 AI 出的題目
- **考慮過的選項**：讓 AI 自己想錯誤選項、從字卡挑
- **選擇的理由**：
  - 規格要求「錯誤選項優先從使用者字卡中的其他單字挑」，這樣考的是自己正在背的字，複習效果更好
  - 程式先挑好錯誤選項（同詞性優先），再請 AI 改成和答案一樣的詞形（例如都改成過去式），這樣四個選項看起來才像真的考題
  - AI 偶爾會出錯，所以每題都要用 `normalizePart5()` 檢查：只能有一個空格、四個選項不重複、答案不能已經出現在句子裡；不合格的題目就丟掉
- **取捨**：被丟掉的題目，那個字這次就不考。畫面會提示「有 N 個字出題失敗」，下次會再試

### 28. Part 5 題目存在單字上重複使用
- **考慮過的選項**：每次都重新出題、存起來重複使用
- **選擇的理由**：
  - 免費額度有限，每個字最多存 3 題，出題時優先用最久沒考過的那題
  - 選項的順序每次都會重新打亂，避免記住答案的位置
  - 想要新題目時，可以勾選「出新題目」
- **取捨**：存檔的題目考久了可能會記住句子，所以提供「出新題目」選項。題目存在單字資料裡，之後匯出／匯入時會一起帶走

### 29. 錯題本存「整題」，而不是只存單字
- **考慮過的選項**：只記哪些字答錯、存完整的題目
- **選擇的理由**：重做時看到的是同一題（特別是 Part 5 的句子），不需要再呼叫 AI。同一題重複答錯時，只把次數加 1，不會重複存
- **取捨**：比較佔空間，所以最多存 300 題。刪除單字時，相關的錯題也會一起清掉

### 30. 測驗答錯只標記「不熟」，不改變複習排程
- **考慮過的選項**：答錯時也把複習排程重設成「10 分鐘後到期」、只標記不熟
- **選擇的理由**：規格是「答錯的字自動標記為不熟」。複習排程只由「複習」頁決定，兩者分開比較好理解，也不會因為測驗時手滑點錯就打亂排程
- **取捨**：測驗答錯的字不會馬上出現在複習清單裡，但可以用「不熟」的範圍去瀏覽或測驗

### 31. 「檢查」和「寫入」之間不能有等待（避免非同步的競態）
- **背景**：一次加入很多字時，字典資料偶爾會蓋掉 AI 剛生成的中文。原因是舊程式先算好要寫入的字典資料，等其他字母的檔案下載完才寫入，這段期間 AI 可能已經寫好了內容
- **考慮過的選項**：每個字查完馬上寫入、加上鎖、先下載完再一次檢查並寫入
- **選擇的理由**：先 `await` 下載好所有需要的字典檔，再同步地讀取最新資料、檢查是否可以寫入、寫入。JavaScript 是單執行緒，同步執行的這一段不會被 AI 的回應插進來
- **取捨**：中文要等這一批的字典檔都下載完才會一起出現，但字典檔在本機，通常不到 1 秒就好

## 第 7 步：學習統計

### 32. 圖表自己用 SVG 畫，不使用圖表套件
- **考慮過的選項**：Chart.js、ECharts、自己用 SVG 畫
- **選擇的理由**：
  - 只需要直條圖一種，自己寫大約 200 行
  - 不需要從外部 CDN 載入套件，第 9 步做 PWA 時離線也能看統計
  - 可以完全照 dataviz 規範控制細節：柱子寬度、圓角、2px 空隙、只標最高值、提示框、表格
- **取捨**：功能比套件少（沒有動畫、縮放），之後如果需要更複雜的圖表，再考慮使用套件

### 33. 「會／不熟」用藍／橘兩個系列色，不用綠／紅
- **考慮過的選項**：綠／紅、藍／橘
- **選擇的理由**：依照 dataviz 規範，綠、紅這類狀態色是保留給「狀態」用的（例如成功、錯誤），而且必須搭配圖示和文字。這裡的兩個系列是分類，所以用系列色。藍／橘兩色用 `validate_palette.js` 對本站的卡片底色驗證：淺色、深色模式都通過，色盲模擬下的色差是 24.7 和 26.8（門檻 8）
- **取捨**：「答錯是橘色」不像紅色那麼直覺，但有圖例和文字標示，不會只靠顏色判斷

### 34. 熟練度用同一個藍色的深淺；深色模式另外挑色並驗證
- **選擇的理由**：
  - 新字 → 學習中 → 熟悉中 → 已熟是「有順序的分組」，所以用同一個色相由淺到深，不用四種不同顏色
  - 深色模式改成「越熟越亮」，因為在深色背景上，越亮越顯眼
  - 第一次挑的深色色階中，最深一階對本站的深灰底色只有 1.87:1，驗證沒有通過；往淺一階換成 `#1c5cab`（2.28:1）才通過
- **取捨**：深色模式要多維護一組顏色，但這些顏色都集中定義在 CSS 變數裡

### 35. 連續學習天數：今天還沒學習時，從昨天開始算
- **考慮過的選項**：嚴格只算到今天（今天沒學就是 0）、今天還沒學時從昨天開始算
- **選擇的理由**：一大早打開網站就看到「連續 0 天」會很打擊信心。從昨天開始算，並提示「今天學習一下就能延續！」，比較能鼓勵使用者。只做測驗、沒有複習，也算有學習
- **取捨**：這個數字代表「到昨天為止」還是「到今天為止」，要看旁邊的提示文字

### 36. 「設定」改成齒輪圖示
- **選擇的理由**：加上「統計」後有 6 個文字項目，手機上排不下，文字還被折成兩行。設定不是每天都會用到，改成和深色模式按鈕並排的圖示（有 `aria-label`）
- **取捨**：設定的入口比較不明顯，但齒輪是大家都認得的圖示

## 第 8 步：匯出／匯入（含追加的口音與每日目標）

### 37. 「多益混合」口音：只從這台裝置有語音的口音中隨機挑
- **背景**：使用者要求加入多益聽力的四種口音（美、英、加、澳）
- **考慮過的選項**：固定一種口音、四種輪流（不管裝置有沒有）、只挑有語音的口音
- **選擇的理由**：
  - 發音靠的是裝置內建的語音（Web Speech API）。如果裝置沒有加拿大語音卻硬要選，瀏覽器會用預設的美式語音，等於「標示是加拿大，聽起來是美國」，這樣會誤導
  - 所以混合模式只挑有語音的口音；手動選了沒有語音的口音時，設定頁會直接說明會用其他語音代替
- **取捨**：可以練到的口音受裝置限制。設定頁有教使用者怎麼新增語音
- **沒有用 AI 產生語音**：Gemini 有語音模型，但需要網路、會用掉額度，而且每個字都要另外處理；內建語音免費又能離線使用，已經夠用

### 38. 只擋滑鼠或觸控產生的重複 click，鍵盤的 click 一律放行
- **背景**：決策 #24 為了避免「點一下」觸發兩次，會擋掉點擊後短時間內的 click，結果連鍵盤觸發的按鈕也被擋掉了
- **選擇的理由**：瀏覽器會把鍵盤觸發的 click 標成 `event.detail === 0`，滑鼠或觸控的則是 1 以上，用這個就能精準區分
- **取捨**：沒有

### 39. 每日目標：達標才算打卡；每天記下當天的目標
- **考慮過的選項**：有學習就算打卡、達標才算打卡、兩種都顯示
- **選擇的理由**：
  - 使用者選了「達標才算」，比較有督促的效果
  - 目標記在每天的紀錄裡，之後調整目標不會改寫過去的打卡；但今天一律用目前的目標，今天把目標調高就要重新達標
  - 複習一張卡或測驗答一題都算 1 題，兩種學習方式都能累積進度
- **取捨**：紀錄多一個欄位；舊資料沒有記下目標，就用目前的目標判斷

### 40. 備份檔不包含 Gemini 金鑰
- **選擇的理由**：備份檔常常會被傳來傳去（寄給自己、放雲端、傳給朋友），金鑰放在裡面很容易外洩。金鑰本來就存在獨立的 localStorage 欄位，匯出時根本不會讀到它
- **取捨**：換裝置後要重新填一次金鑰。設定頁有說明

### 41. 匯入時每個欄位都重新檢查和清理
- **考慮過的選項**：直接寫入、只檢查格式、逐欄清理
- **選擇的理由**：備份檔可能被改過、壞掉，或根本是別的檔案。逐欄清理的做法：
  - 型別不對就改成預設值，數字限制在合理範圍
  - 不認得的設定和欄位丟掉
  - 錯題的選項必須剛好 4 個
  - 單字必須含有英文字母
- **取捨**：程式比較長，但壞檔案不會讓網站壞掉。另外畫面一律跳脫 HTML，被竄改的內容也不會被執行（有測試驗證）

### 42. 合併的規則：最後修改的版本勝出，每日紀錄取較大值
- **考慮過的選項**：一律以備份為主、一律以目前為主、依修改時間決定
- **選擇的理由**：
  - 同一個字，留下 `updatedAt` 比較新的版本，哪台裝置最後改過就以哪台為準
  - 每日紀錄同一天的每個欄位取較大值，而不是相加。這樣同一份備份匯入兩次結果也不會變，使用者不小心重複匯入也沒關係
- **取捨**：如果兩台裝置在同一天都有複習，合併後的次數會偏少（取較大值，而不是相加）。這是為了避免重複計算所做的選擇；真正的跨裝置同步要等之後接上雲端資料庫

## 第 9 步：PWA

### 43. 網站檔案「先連網、斷線才用快取」；字典與字型「有快取就用快取」
- **考慮過的選項**：
  - 全部先用快取，加上版本號：最快，但每次更新都要記得改版本號，忘了改的話使用者會一直停在舊版
  - 先用快取，同時在背景更新：一次載入可能混用新舊版本的 JS 模組，容易出錯
  - 網站檔案先連網
- **選擇的理由**：
  - 這個專案沒有建置步驟，也是初學者在維護，「不用記得改版本號」最重要
  - 有網路時一定拿到最新版；離線時用上次的版本，也不會新舊混用
  - 加上 4 秒逾時，訊號很差時不會一直等
  - 字典檔大而且幾乎不變，字型網址本身就帶版本，所以這兩種有快取就用快取
- **取捨**：
  - 有網路時每次都要連網，第二次以後開網站，會比「全部先用快取」慢一點
  - 字典重新產生時，要把 `sw.js` 的 `DICT_CACHE` 版本號加 1

### 44. 由頁面告訴 Service Worker 要快取哪些檔案，不手動維護清單
- **考慮過的選項**：在 `sw.js` 手動列出所有檔案、用建置工具自動產生清單、頁面載入後回報
- **選擇的理由**：
  - 第一次開網站時 Service Worker 還沒接手，所以第一次載入的檔案它攔不到
  - 頁面用 `performance.getEntriesByType('resource')` 取得這次實際載入的所有檔案（含字型），傳給 Service Worker 一次存起來
  - 以後新增 JS 檔案，不用回頭修改 `sw.js`
- **取捨**：只會快取「這次用到的檔案」。因為 `app.js` 一開始就載入所有頁面的模組，所以實際上是全部

### 45. 離線時 AI 生成「暫停」，而不是「失敗」
- **背景**：原本連不上 Gemini 時，會把整批字標成「生成失敗」，使用者要手動重試
- **選擇的理由**：離線是暫時的，和「金鑰錯誤」「額度用完」一樣應該暫停，這些字不算失敗。重新連上網路時（`online` 事件），自動補查字典並繼續生成
- **取捨**：沒有

### 46. 安裝方式：Chrome／Edge 顯示按鈕；iPhone 顯示教學
- **選擇的理由**：
  - Chrome／Edge 會發出 `beforeinstallprompt` 事件，可以攔下來，改在設定頁放「安裝」按鈕，不會突然跳出提示打擾使用者
  - iPhone 的 Safari 不支援這個事件，只能教使用者用「分享 › 加入主畫面」
  - iPhone 上主畫面 App 和 Safari 的儲存空間是分開的，這點很容易造成「資料不見了」的誤會，所以特別提醒先匯出、再匯入
  - 同時呼叫 `navigator.storage.persist()`，請瀏覽器不要在空間不足時自動清除資料
- **取捨**：iPhone 使用者要自己照步驟操作

### 47. 把模型的「思考」降到最低，不支援時自動換設定並記住
- **背景**：使用者實際使用時，AI 生成很慢或生不出來。新版 Flash 模型預設會先思考，思考的 token 又算在輸出上限裡，容易被截斷、觸發拆半重送
- **考慮過的選項**：
  - 只降低 `maxOutputTokens`：思考還是會發生，反而更容易被截斷
  - 依模型名稱寫死某一種設定：模型和規則常常變動
  - 依模型先試最省的設定，不支援就自動換
- **選擇的理由**：這個網站的工作（產生解釋、例句）不需要推理。Gemini 2.5 先試 `thinkingBudget: 0`，其他模型依序試 `minimal` → `low` → 不帶設定；收到和 thinking 有關的 400 錯誤就換下一個，並記住可用的設定。以後 Google 換模型，也不容易壞掉
- **取捨**：第一次遇到不支援的模型，會多花一次請求（只會發生一次）；內容品質可能稍降，但這種任務影響不大，可以用「測試 AI」確認

### 48. 第一批只送 5 個字
- **選擇的理由**：一批 20 個字要等整批生成完才會顯示，使用者會覺得「沒反應」。第一批改成 5 個字，幾秒內就能看到結果，之後每批再恢復 20 個字，以節省請求次數
- **取捨**：字數不是剛好的時候，偶爾會多一次請求（例如 40 個字會分成 5、20、15 三次）

### 49. 提供診斷工具，而不是只靠猜
- **選擇的理由**：
  - 開發時用的是假的 AI 回應，測不出真實的速度和品質
  - 記錄每次請求的耗時和 token 數、提供「測試 AI」按鈕之後，使用者自己就能看到問題，也能把數字回報給開發者
  - 有思考 token 的話，代表思考沒有被關掉
- **取捨**：沒有

## 第 10 步：部署

### 50. GitHub Pages 直接從 main 分支的根目錄部署，不用 GitHub Actions
- **考慮過的選項**：從分支部署、用 GitHub Actions 建置後部署
- **選擇的理由**：這個網站沒有建置步驟，push 上去的檔案就是網站本身，所以不需要另外寫部署流程；push 之後大約 1 分鐘就會自動更新。網址全部用相對路徑，放在 `/toeic-cards/` 子路徑下也能正常運作
- **取捨**：repo 裡的測試、文件、工具也會被放在網站上（例如 `/toeic-cards/docs/`）。這些本來就是公開的作品集內容，所以沒有影響；之後如果要排除，再改用 Actions 只部署需要的檔案

## 第 11 步：跨裝置同步

### 51. 雲端以「單字」為單位存放，只同步有變動的部分
- **考慮過的選項**：整份資料存成一份文件、每個字一份文件
- **選擇的理由**：
  - 一份 Firestore 文件最大 1MB，1,000 個字加上 AI 內容就會超過
  - 每個字一份文件的話，可以只傳有變動的字：上傳時比對「上次上傳的版本」，下載時用伺服器時間 `syncedAt` 查詢「上次之後有變動的字」
  - 不同裝置的時鐘可能不準，所以「拉到哪裡」用伺服器時間記錄
- **取捨**：刪除也要同步，所以要留下「刪除紀錄」（tombstone），而且會一直保留

### 52. 每日紀錄各裝置分開記，顯示時加總
- **背景**：備份合併用的「每天取較大值」，在兩台裝置同一天都有學習時會少算，害使用者打卡失敗
- **選擇的理由**：
  - 每台裝置只寫自己的紀錄（`logs/{裝置 id}`），所以不會互相覆蓋
  - 顯示時把所有裝置加總：次數相加，每日目標取較大值
  - 本機原本的 `toeic-cards:log` 改成「這台裝置自己的」，其他裝置的另外存放；`getLog()` 回傳加總後的結果，統計、打卡的程式完全不用改
- **取捨**：用備份檔搬到另一台裝置，又同時開啟同步的話，那份紀錄可能被算兩次（很少見，文件中有說明）

### 53. Google 用彈出視窗登入，Email 連結登入另外提供「貼上連結」
- **背景**：官方文件說明，Chrome 115+、Safari 16.1+、Firefox 109+ 會擋第三方儲存空間，網站不在 Firebase 網域時，「跳轉登入」會失敗
- **選擇的理由**：
  - 彈出視窗在任何網址都能用
  - Email 連結登入給沒有 Google 帳號，或彈出視窗被擋的情況使用
  - iPhone 主畫面 App 點信件連結會開啟 Safari（兩邊的資料分開），所以提供「長按連結 › 拷貝 › 回到 App 貼上」的方式
- **取捨**：彈出視窗可能被瀏覽器擋住，錯誤訊息會提示改用 Email 登入

### 54. 會在背景更新的表單，重畫時要保留使用者輸入的內容
- **背景**：Firebase 在背景載入完成時，會重畫登入區塊，清掉使用者正在輸入的 Email（測試抓到的）
- **選擇的理由**：
  - 用「看得到的狀態」算出一個比較值，沒變就不重畫
  - 需要重畫時，保留輸入框的內容、`<details>` 是否展開，以及游標所在的欄位
  - 這比「改成只更新部分畫面」簡單，也適用以後新增的欄位
- **取捨**：重畫前後要多做一點保存和還原

### 55. 用 Firebase 官方的本機模擬器測試，不碰正式專案
- **考慮過的選項**：用假的資料庫物件測試、用 Firebase 模擬器
- **選擇的理由**：
  - 模擬器跑的是**真正的 Firebase SDK**，也會套用專案的 `firestore.rules`，所以能驗證「別人讀不到我的資料」這類安全規則
  - 也能測試 Google 彈出視窗登入、Email 連結登入（從模擬器 API 拿到登入連結）
  - 專案名稱用 `demo-` 開頭，不需要登入 Google，也不會產生費用
- **取捨**：需要 Java，還要另外安裝 firebase-tools（只裝在暫存資料夾，不放進網站）

### 56. iPhone 主畫面 App 只提供 Email 連結登入，並在 Safari 頁面提供「複製登入連結」
- **背景**：使用者實際在 iPhone 主畫面 App 按 Google 登入，沒有任何反應。App 模式下，Apple 不讓網頁開啟登入視窗
- **考慮過的選項**：
  - 改用跳轉登入：GitHub Pages 不在 Firebase 網域，會被 Safari 擋下（決策 #53）
  - 加一層後端產生登入權杖：違反「純前端」的設計
  - 用 Email 連結登入，並讓「從 Safari 帶回 App」這一步更順
- **選擇的理由**：
  - 偵測到 iPhone App 模式時，不顯示 Google 按鈕，並說明「輸入和電腦同一個 Gmail，就是同一個帳號」（有用模擬器驗證）
  - 點信裡的連結會開啟 Safari，Safari 頁面的主要按鈕是「複製登入連結」，只複製、不用掉連結，回 App 貼上即可登入
- **取捨**：iPhone App 登入要多切換一次 App；第一次登入之後就會一直保持登入

### 57. 加上「Email＋密碼」登入，作為 iPhone 主畫面 App 的主要方式
- **背景**：Firebase 免費方案整個專案每天只能寄 5 封登入連結信（官方 limits 文件），使用者在 iPhone App 寄信就收不到了
- **考慮過的選項**：
  - 升級 Blaze 方案：需要綁信用卡
  - 叫使用者明天再試：治標不治本
  - 加上不需要寄信的 Email＋密碼登入
- **選擇的理由**：
  - 密碼登入不用寄信，也不需要彈出視窗，在 iPhone App 裡一定能用
  - 電腦用 Google 登入後可以「設定密碼」，把密碼加到同一個帳號
  - 「加上密碼」被拒絕時（例如模擬器，或者這個 Email 已經用連結登入過），改成直接更新密碼，結果一樣是同一個帳號
- **取捨**：使用者要多記一組密碼；忘記密碼時要寄重設信（這類信的上限是每天 150 封，比較寬鬆）

## 第 12 步：自訂單字集

### 58. 單字集獨立存放，同一個字共用內容與複習進度
- **決策**：單字集使用固定 id，名稱可以修改；每個集以單字本身記錄成員。一張卡可屬於多集，卡片和 SRS 仍只有一份。
- **考慮過的選項**：每集複製一份字卡、卡片只能選一個分類、獨立單字集搭配多對多成員關係。
- **選擇的理由**：「財務」與「第 3 回模考」可以重疊；固定 id 讓改名不影響歸屬，以單字對應可跨越各裝置不同的卡片 id。舊單字不需搬移，未加入任何有效集的字顯示在「未分類」。
- **取捨**：所有單字集共用熟練度，無法在不同集重新計算同一字的進度。目前選的範圍只留在本機，不讓手機切換範圍影響電腦；每日新字上限與打卡仍是全站合計。

### 59. 單字集依成員合併，使用 Firestore 交易避免整份互蓋
- **決策**：集的名稱／刪除狀態和每個成員的加入／移出分開記時間；同步時在 `users/{uid}/meta/wordSets` 用交易讀取最新內容後合併。
- **考慮過的選項**：整份資料最後修改者勝出、把集放進學習設定、每個成員各一份 Firestore 文件、單一文件內逐項合併。
- **選擇的理由**：手機移出一個字、電腦新增另一個字，兩個操作都要保留；改名也不能覆蓋成員。移出和刪除留下紀錄，較舊的離線裝置不會把它們加回。交易遇到其他裝置同時寫入會重試，避免讀完後再整份覆蓋。
- **取捨**：使用裝置時間判斷先後，和既有同步一樣受到裝置時鐘影響；同一時間衝突用固定規則處理，移出／刪除優先。每次同步需讀取整份分類文件，並受 Firestore 單文件大小限制；一般數千字的個人單字庫適用，大量分類與成員應改為分文件。安全規則沿用每人只能讀寫自己的路徑。

### 60. 備份升為版本 2，仍可讀取版本 1
- **決策**：備份增加 `wordSets`，格式版本改為 2；舊版沒有分類的備份視為空單字集。合併使用相同的成員合併規則。
- **考慮過的選項**：把分類藏在既有欄位維持版本 1、明確升版並保留舊檔讀取能力。
- **選擇的理由**：舊程式不認得分類，如果仍標版本 1，使用者可能在舊版匯入後無聲丟失分類；升版可提示先更新網站。取代還原是一個新的操作，會為被取代的分類與成員留下較新的刪除／移出紀錄，防止雲端舊資料復活。
- **取捨**：舊版網站要先更新才能讀新版備份；刪除紀錄仍保存在備份中，資料量會比只匯出可見分類稍大。

## 第 13 步：內建多益單字包

### 61. 單字包使用獨立 JSON，保留原序並記錄拼字修正
- **決策**：從提供的 PDF 只整理英文選字，放在 `data/packs/toeic-1000.json`；保留順序，每 100 字一組。記錄來源雜湊與經人工核對的三筆拼字修正。
- **考慮過的選項**：直接把 PDF 放上網站、複製全部翻譯與例句、只內建選字再沿用字典與 AI。
- **選擇的理由**：資料檔小、不需使用者上傳或解析 PDF，也能清楚區分來源選字與網站自己的詞義內容。加入時使用結構化陣列，不經一般貼上拆字器，避免破壞 `résumé`；Unicode 組合形式統一為 NFC，但不把 `résumé` 與 `resume` 混為一字。
- **取捨**：分組只是原順序的切分，不是難度或主題分級。來源的三筆明顯錯字修正後收錄，不以錯字建立卡片；未收錄原 PDF 的翻譯或例句。

### 62. 單字包加入沿用單字集，既有字只新增歸屬
- **決策**：預覽列出新字、已有字與已在目標集的字；可建立自訂名稱或選現有集，同名時沿用。每次只為新的字查字典或啟動使用者勾選的生成。
- **考慮過的選項**：每組建立新集、加入就覆蓋全部內容、把每次加入視為同一目標集的追加。
- **選擇的理由**：分批學習不會留下十個同名或重複的分類，已經整理過的字與進度也不會被覆蓋。既有備份與同步可直接使用分類成員資料，不需另一套單字包進度。
- **取捨**：內建包的「已有」以目前單字庫為準；改拼字或刪除單字後，原包中的字會重新成為可加入項目。單字包開啟時才載入，首次離線且尚未載入過時需先連線；載入後由 Service Worker 快取供離線使用。

### 63. 批量加入不自動使用 AI 額度，記住每個新字的選擇
- **決策**：單字包 AI 選項預設不勾選，新字記下 `autoGenerate: false`；重新連線的自動生成略過這些字，手動生成仍可執行，標記會隨備份與同步保留。
- **考慮過的選項**：完全沿用全站自動生成、只在加入當下不呼叫 AI、把不自動生成的選擇存在每張卡。
- **選擇的理由**：只控制當下不足以避免下次連線突然生成 1,000 字，必須讓選擇跨重新整理、備份和裝置保留。字典為全部選字提供基本中文；子集缺少的 15 詞與 `download` 的明顯錯義由專案補充詞義模組處理。
- **取捨**：目前不附預先生成的英文解釋與例句；勾選生成時仍需個人 Gemini 金鑰。這份固定清單未來可改為隨網站提供經檢查的生成內容，便能省去使用者的生成等待與個人額度。

## 第 14 步：單字包預製學習內容

### 64. 固定清單隨網站提供完整內容，不替使用者逐次生成
- **決策**：為 1,000 字預先撰寫中文、淺白英文解釋、一組雙語例句與搭配詞，按原序編成十份靜態 JSON；詞形參考 ECDICT，部分字另補同義詞。這項決策取代第 63 條對固定單字包的即時生成安排。
- **考慮過的選項**：每位使用者自行用 Gemini 生成、站方建立共用生成後端、隨網站提供固定版本內容。
- **選擇的理由**：選字固定，反覆生成相同字卡會浪費等待時間與個人額度；靜態內容可直接部署 GitHub Pages，不需站方金鑰或後端。開啟入口時載入全部十份（約 336 KB），成功後可離線選任一組加入；尚未開啟時不下載。
- **取捨**：每字先提供一組雙語例句，並非個人 Gemini 生成的兩組；內容由 AI 撰寫，結構驗證與抽查不等於專業教師審訂。保留可編輯能力及來源資料，後續勘誤可查閱歷史。Part 5 即時出題仍使用個人金鑰。

### 65. 預製內容與個人生成分開記錄，舊卡補寫必須明確選擇
- **決策**：加入新字時一次寫入完整內容與 `src: pack`／內容版本，避免空白字卡先觸發自動生成；生成計數及批次重試略過完整包內容，不偽造 Gemini 成功紀錄。備份與同步保留這些標記。
- **考慮過的選項**：把預製內容標成 `llm: done`、只禁止加入當下生成、辨識靜態來源並沿用原儲存流程。
- **選擇的理由**：即使已有金鑰、重新連線或按「生成缺項」，也不應重送完整字卡。已有字預設只增加單字集歸屬；明確勾選補空白後，只補沒有內容且未標記 `user` 的欄位，保留個人修改、刻意清空和 SRS。
- **取捨**：一張舊卡可混合個人與內建內容，需保留逐欄位來源；整張卡的「內建」標籤表示含有內建內容，並非所有欄位都未經修改。後續內容更新不強制覆寫已加入的卡片。

## 第 15 步：全站查字與單字庫用途分離

### 66. 查字典使用全站視窗，單字庫保留收藏管理
- **決策**：上方提供固定的「查單字」按鈕及 Ctrl／⌘ K，以原生 dialog 查詢；單字庫的搜尋明確命名「搜尋我的字卡」。查字本身不新增卡片、不更新 SRS 或學習紀錄。
- **考慮過的選項**：只把原本篩選框移到頂列、另設完整字典頁、全站可開啟的查詢視窗。
- **選擇的理由**：查任何英文和篩選收藏是兩種用途；視窗保留目前頁面與題目，關閉即可繼續學習。沿用原生 dialog 的焦點限制與既有快捷鍵防誤觸機制，手機也能直接使用。
- **取捨**：查詢先顯示本機中文，英文解釋由使用者按鈕明確查詢；不提供模糊搜尋、逐字建議或 AI 聊天。關閉或另查新字會中止舊英文請求並忽略過期結果；收藏只寫入已查到的資料，不自動使用 Gemini 或背景補英文。

### 67. 新增與分類各用獨立工具，清單預設收合低頻操作
- **決策**：「＋加入單字」整合輸入、批次貼上、內建單字包三種方式；分類管理另外開窗。批次整理與閒置 AI 工具收合，生成中／失敗時才將狀態提升到清單上方。手機頂列採兩排，讓查字入口保有文字。
- **考慮過的選項**：維持全部表單堆疊、增加更多導覽頁面、用視窗隔開新增與管理。
- **選擇的理由**：以收藏清單為預設工作區，低頻工具按需打開；沿用既有儲存、去重、備份與同步邏輯，不改卡片資料格式。原單字包直接連結仍會打開對應方式，避免舊連結失效。
- **取捨**：新增或管理多一次開窗；保留工具內的輸入草稿與目前分組，讓重複操作仍順手。既有端對端測試需使用新入口，透過共用 helpers 點擊真實按鈕，不以測試專用介面繞過操作。

## 第 16 步：單字探索與今日複習分工

### 68. 探索直接閱讀內容，複習維持回想與排程
- **決策**：原自由字卡改為「單字探索」，從目前單字集搜尋與選字，直接閱讀雙語解釋及延伸內容；僅今日複習提供翻面與「會／不熟」評分。
- **考慮過的選項**：把兩頁合併成學習模式切換、探索與複習分工、另建立預習完成狀態。
- **選擇的理由**：使用者選擇用途分離。探索忽略到期與每日新字數，方便查閱任何已收藏字；不新增學習狀態或複製資料。篩選與選字以純函式處理，先獨立測試再接介面。
- **取捨**：探索取消翻面與滑動手勢，以閱讀清單與上一字／下一字取代。保留既有 `#/cards` 連結與不熟篩選設定；單字識別與進度共用原卡片，不另外建立探索進度。

### 69. 探索使用清單搭配閱讀詳情，保留搜尋焦點與背景更新
- **決策**：桌面左右並排，手機上下排列且限制清單高度；中英解釋同時顯示，延伸內容沿用共用 renderer。查詢輸入與頁面骨架保持原節點，清單與詳情只在內容改變時更新。
- **考慮過的選項**：沿用翻卡再加說明、每字跳到另一頁、單頁清單與完整閱讀內容。
- **選擇的理由**：從操作與版面一起區分探索和複習；保留目前字與查詢，在分類、同步或刪除後只選有效的收藏。背景查字與生成更新不應打斷搜尋輸入或每秒重建整份清單。
- **取捨**：手機需在清單與閱讀內容間捲動；點字時將詳情帶入畫面。上一字／下一字在當前篩選範圍循環。選字和搜尋只在本次頁面工作階段保留，不上傳或改成學習進度；完整重新整理後從有效第一字開始。
